# 技术设计说明

> 本文档说明「公文合规审查与督办助手」（`official-document-assistant`，v0.8.0）的整体架构、模式组合、数据流、关键设计决策与扩展点。
> 主脚本：`scripts/gov_doc_review.py`。配套知识库：`references/`。测试：`tests/`。

## 一、为什么是两层架构

办公室材料反复退回的真正原因，往往不是"写得不好"，而是**格式要素不齐、文种混用、敏感信息没脱敏、会议待办没人跟**。这些问题有三个共同特征：

1. **需要精确**：标题三要素、成文日期格式、附件编号、主送机关——这些是"对就是对、错就是错"的客观判断，容不得"差不多"。
2. **需要可复现**：同一份材料今天审查和明天审查，结论应当一致；不同审查人之间也应当一致。
3. **需要可追溯**：每一条意见都应当能指到 GB/T 9704—2012《党政机关公文格式》或《党政机关公文处理工作条例》的具体要素。

而这恰恰是当前大模型在零样本、无工具调用场景下的弱项：模型容易在格式要素上"幻觉"（把不规范的日期判成规范、把缺失的主送机关补出来）、在敏感信息上"自作主张"（直接改写而不提示风险）、在依据上"编造条款号"（给出一个看似权威但并不存在的"第 X 条"）。

因此本 Skill 刻意分成两层，各做自己擅长的事：

### 1. 智能体层（宿主大模型承担）

- 语义理解：判断用户意图是审查、起草、督办提取还是版本对比。
- 文种复核：脚本给出文种初判，模型可结合上下文做最终确认。
- 修订润色：在脚本给出的"建议修订稿"骨架上做语言层面的润色，但不得编造未提供的事实。
- 起草生成：在脚本给出的草稿骨架上填入真实、可执行的内容，避免套话。
- 异常引导：对偏题、信息缺失、损坏文件等情况，向用户给出友好澄清，而不是硬套模板。

### 2. 确定性校验层（本仓库脚本 `scripts/gov_doc_review.py`）

- 纯 Python 标准库实现，**不调用任何模型**。
- 对格式要素、文种规则、敏感信息做可复现、不幻觉的检查与本地脱敏。
- 输出结构化结果（Markdown 报告 / JSON / CSV），供智能体层二次加工或直接呈现给用户。
- 每条问题附 `basis` 依据字段，指向 GB/T 9704—2012 或条例的要素名称与原则。

### 3. 为什么要这样分

| 关注点 | 智能体层 | 确定性校验层 |
| --- | --- | --- |
| 格式要素（标题/日期/落款/附件） | 复核 | **主判** |
| 文种规则（一文一事/报告不夹带请示） | 复核 | **主判** |
| 敏感信息脱敏 | 不参与 | **主判**（本地脱敏） |
| 涉密材料提示 | 引导用户 | **主判**（只提示不处理） |
| 修订稿语言润色 | **主判** | 给骨架 |
| 起草内容生成 | **主判** | 给骨架 + 自检 |
| 异常输入引导 | **主判** | 给分诊信号 |
| 依据可追溯 | 不编造 | **主判**（basis-map.json） |

核心原则：**判断和改写交给模型，合规校验和脱敏交给确定性程序**。这样既避免模型在格式要素和敏感信息上幻觉，也让每条意见都能追溯到国标与条例。

## 二、五个核心模式及其组合

本 Skill 提供 5 个可组合的核心模式，覆盖办公室正式材料流转的完整闭环：

| 模式 | 用途 | 典型输入 | 输出结构 |
| --- | --- | --- | --- |
| `review` | 公文格式与合规审查 | 通知/请示/报告/函/会议纪要正文 | 三层报告（领导摘要 / 承办人修改清单 / 建议修订稿）+ 督办事项 + 脱敏预览 |
| `draft` | 根据一句话或 JSON 需求生成草稿骨架 | "帮我写一份关于……的通知" | 可编辑草稿 + 起草信息缺口 + 自动合规自检 |
| `brief` | 会议纪要/简报督办台账提取 | 会议纪要正文 | 督办台账表（Markdown 表格或 CSV） |
| `compare` | 两版材料版本变更说明 | `--old old.md --new new.md` | 核心变化 + 风险变化表 + 提交建议 |
| `batch` | 批量材料包体检 | `--batch examples/review` | 总览 + 文件风险排行表 + 跳过清单 |

### 模式如何组合

1. **draft → review（自检）**：`draft` 模式生成草稿骨架后，会自动调用 `analyze()` 跑一遍 review 自检，输出"草稿 + 信息缺口 + 自检报告"。这是 v0.8.0 的关键升级——起草即自检，避免"起草完还要手动审查一遍"。

2. **review → 督办事项**：`review` 模式在审查公文的同时，会调用 `extract_supervision_items()` 提取督办事项，附在报告第五节。这样审查一份通知的同时就拿到了督办台账。

3. **compare → review（双侧）**：`compare` 模式对旧版和新版各跑一遍 `analyze()`，对比两侧的风险等级和问题集合，输出风险变化表。这是"审查能力"的复用。

4. **batch → review（逐文件）**：`batch` 模式对目录内每个文件调用 `analyze()`，汇总成风险排行表。单文件出错不影响整体，记入跳过清单。

5. **brief = review 的督办子集**：`brief` 模式复用 `analyze()` 的督办事项提取逻辑，但输出格式改为督办台账表（Markdown 表格或 CSV），可直接贴入 Excel 或任务系统。

## 三、数据流

主脚本的数据流如下（以 `review` 模式为例）：

```
stdin / --input 文件
        │
        ▼
   read_input()          ── 读取 UTF-8 文本 / Markdown / JSON / .docx
        │                    .docx 走 read_docx_text()，提取段落 + 表格 + 批注/修订信号
        │                    非 UTF-8 用 errors="replace" 读取，不崩溃
        ▼
   sanitize_text()       ── 去除控制字符（\x00-\x1f\x7f）
        │
        ▼
   triage_input()        ── 分诊：空输入 / 起草请求误投 / 过短非公文 → 返回 "# 输入提示"
        │                    分诊通过才进入正式审查
        ▼
   extract_structure()   ── 结构抽取：标题 / 主送机关 / 落款 / 成文日期 / 附件 / 正文
        │                    detect_doc_type() 识别文种（通知/请示/报告/函/纪要/简报/方案/通报）
        ▼
   check_document()      ── 规则检查
        │   ├─ check_common_rules()   通用规则（标题/主送/落款/日期/附件/层级/口语化/强制表述/PII/涉密）
        │   └─ check_doc_type_rules() 文种规则（请示一文一事/报告不夹带请示/函语气/通知可执行性）
        ▼
   score_document()      ── 评分：high -14 / medium -8 / low -4，分四维（格式/结构/语言/风险）+ 总分
        │                    风险等级：≥85 低 / ≥70 中 / <70 高；涉密或 PII 强制为高
        ▼
   build_suggested_revision()  ── 生成建议修订稿（可复制再人工复核）
        │
        ▼
   extract_supervision_items() ── 提取督办事项（责任方/任务/截止时间/原文依据）
        │
        ▼
   build_redacted_preview()    ── 本地脱敏预览（手机号保留前3后4，身份证号保留前6后4）
        │
        ▼
   build_markdown()      ── 组装三层报告
        │
        ▼
   stdout / --output 文件
```

### 关键节点说明

- **read_input**：统一入口，支持 stdin、UTF-8 文本、Markdown、JSON、`.docx`。`.docx` 用 `zipfile` + `xml.etree.ElementTree` 解析（纯标准库），提取 `word/document.xml` 中的段落（`w:p`）和表格（`w:tbl`），并检测 `word/comments.xml`、`w:ins`、`w:del` 信号。
- **triage_input**：v0.5 引入的"友好分诊"。空输入、起草请求误投审查模式、过短非公文文本，都返回 `# 输入提示` 而非错误报告，避免产出误导性的 0/100 报告。
- **extract_structure**：基于行首特征启发式抽取。主送机关识别"以冒号结尾且长度 ≤60 的非抄送/附件/密级行"；成文日期识别 `YYYY年M月D日` 与 `YYYY-MM-DD` 两种格式（后者会被标记为不规范）。
- **check_document**：分通用规则 + 文种规则两层。通用规则对照 GB/T 9704—2012 主体要素；文种规则对照条例中请示/报告/函/通知的适用范围与行文要求。
- **score_document**：四维评分（格式/结构/语言/风险）+ 总分。涉密或 PII 强制将风险等级提升为"高"，避免"分数高但实际有敏感信息"的误判。
- **build_markdown**：组装三层报告。领导摘要（一句话结论 + 风险等级 + 三大主要问题）→ 结构识别 → 承办人修改清单（表格）→ 建议修订稿 → 督办事项（表格）→ 脱敏预览。

## 四、关键设计决策

### 1. 零依赖、纯标准库

脚本仅 import：`argparse`、`csv`、`io`、`json`、`re`、`sys`、`zipfile`、`dataclasses`、`pathlib`、`typing`、`xml.etree.ElementTree`。**不依赖任何第三方包**。

这意味着：
- 部署时无需 `pip install`，只要有 Python 3.8+ 即可运行。
- 不会因为依赖版本冲突、供应链投毒、镜像源不可用等问题导致部署失败。
- 适合在 AstronClaw / SkillHub 等受控环境稳定运行。
- `.docx` 解析不依赖 `python-docx`，而是直接用标准库 `zipfile` + `ElementTree` 读取 OOXML，避免引入重依赖。

### 2. 零联网、数据不出域

脚本不发起任何网络请求，不调用任何外部模型 API，不访问任何外部服务。所有处理在本地完成。

- 不存在"用户文档被上传到第三方"的风险。
- 涉密材料、个人隐私材料可以放心交给脚本处理（脚本只读取、不外传）。
- 适合在内网、离线环境运行。

### 3. 友好分诊代替 traceback

v0.5 的核心加固：**任何输入都不再抛 raw traceback**。

- 空输入、过短输入、起草请求误投审查模式 → `# 输入提示` + 引导话术。
- 损坏 `.docx`（非 zip / 缺 `word/document.xml` / XML 解析失败）→ `# 输入提示` + 友好说明。
- 文件不存在、路径不是文件 → `# 输入提示` + 路径回显。
- 非 UTF-8 文件 → `errors="replace"` 读取，用替换字符代替非法字节，不崩溃。
- 入口 `try/except` 兜底，任何未预期错误返回"已安全退出"，不抛 raw traceback。

这样智能体层拿到的永远是结构化文本，可以直接转述给用户，而不是把 Python 报错堆栈丢给用户。

### 4. 三层报告结构

v0.8.0 的审查报告刻意分三层，对应办公室真实流转角色：

| 层 | 受众 | 内容 | 设计意图 |
| --- | --- | --- | --- |
| 一、领导摘要 | 处室负责人 | 一句话结论 + 风险等级 + 综合评分 + 三大主要问题 | 10 秒内判断"能不能签发" |
| 二、结构识别 | 承办人 | 标题/主送机关/落款/日期/附件识别结果 | 让承办人知道脚本"看懂了什么" |
| 三、承办人修改清单 | 承办人 | 表格：序号/严重程度/问题/原文证据/修改建议/依据 | 逐条对照修改，每条有依据 |
| 四、建议修订稿 | 承办人 | 一版可复制、可人工复核的规范文本 | 不用从零改起 |
| 五、督办事项 | 督办员 | 表格：序号/责任方/待办事项/截止时间/原文依据 | 审查即督办 |
| 六、脱敏预览 | 承办人 | 手机号/身份证号本地脱敏后的文本预览 | 提交前确认 |

这种分层避免了"一份报告所有人都要从头读到尾"的低效，也让每个角色都能拿到自己关心的部分。

### 5. 依据可追溯（basis-map.json）

`references/basis-map.json` 是问题类型到依据的结构化映射，保证输出依据统一、可追溯。

- 每个问题类型（如 `missing_sender`、`bad_date_format`、`report_with_request`）都有对应的 `basis`（国标/条例要素）和 `human_readable`（人话解释）。
- 脚本在 `check_common_rules()` 和 `check_doc_type_rules()` 中为每条问题附 `basis` 字段。
- **不编造具体条款号**：依据只指向 GB/T 9704—2012 与条例的要素名称和原则（如"主体·成文日期""报告与请示分立"），不写"第 X 条第 Y 款"，避免幻觉。
- 组织可在该文件追加本单位内部规则，扩展为内部依据库。

### 6. .docx 解析的克制

`.docx` 解析只提取正文段落 + 表格文本，并检测批注/修订痕迹信号。**不解析页眉、页脚、版记**，也不解析具体的批注内容和修订内容。

理由：
- 页眉/页脚/版记通常是版式信息，与正文合规性关系不大，强行解析反而引入噪声。
- 批注和修订痕迹的语义复杂（谁改的、什么时候改的、改了什么），规则化解析收益低、误报高。
- 但**检测到**批注/修订痕迹时必须提示用户"提交前确认是否接受全部修订并删除批注"，这是公文正式性的硬要求。

这种"检测但不解析"的克制，是在"信息完整性"和"解析可靠性"之间的合理取舍。

## 五、扩展点

### 1. references/ —— 组织内部规则库

`references/` 目录是供智能体层查阅的领域知识库，组织可在该目录追加本单位行文规则：

- `gongwen-checklist.md`：公文主体要素清单、文种适用范围与易错点。组织可追加本单位行文细则（如"我单位通知必须抄送纪检处"）。
- `drafting-guide.md`：分文种起草规范与异常输入引导话术。组织可追加本单位常用表述模板。
- `basis-map.json`：问题类型到依据的映射。组织可追加本单位内部制度作为依据来源。
- `safety-policy.md`：安全合规策略。组织可追加本单位保密要求。

智能体层在生成修订稿或起草时，可查阅这些文件，确保输出符合组织内部规则。

### 2. basis-map.json —— 依据可追溯

`basis-map.json` 的 `mappings` 字段是问题类型到依据的字典。脚本目前内置 20 个映射（`missing_title`、`title_not_official_pattern`、`missing_sender`、`bad_date_format`、`report_with_request`、`letter_wrong_tone`、`notice_not_actionable`、`docx_tracked_changes` 等）。

扩展方式：
- 组织在 `mappings` 中追加新的问题类型（如 `missing_cc`、"缺少抄送机关"），并指定对应的 `basis` 和 `human_readable`。
- 在 `check_common_rules()` 或 `check_doc_type_rules()` 中追加对应的检查逻辑，引用新映射。
- 这样输出报告中的依据字段就会自动指向组织内部制度，实现"本单位规则可追溯"。

### 3. 文种规则扩展

`DOC_TYPES` 列表和 `check_doc_type_rules()` 函数是文种规则的扩展点：

- 当前支持：通知、请示、报告、函、纪要、简报、方案、通报。
- 组织可追加本单位常用文种（如"决定""意见""批复"），并在 `check_doc_type_rules()` 中追加对应的行文规则检查。

### 4. 模式组合扩展

五个模式是可组合的工具，智能体层可按需编排：

- 用户说"帮我审查这批材料"→ `batch` 模式。
- 用户说"帮我起草一份请示"→ `draft` 模式（自动自检）。
- 用户说"把这份会议纪要的待办整理成台账"→ `brief` 模式。
- 用户说"对比这两版通知"→ `compare` 模式。
- 用户说"审查这份通知并提取督办"→ `review` 模式（自带督办事项）。

未来可扩展的模式：`policy_check`（政策一致性检查）、`accessibility_check`（无障碍格式检查）等，均可在现有 `analyze()` 框架上扩展。
