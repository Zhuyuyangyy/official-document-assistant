# 安全合规说明

> 本文档说明「公文合规审查与督办助手」（`official-document-assistant`，v0.8.0）在数据处理、敏感信息、涉密材料、依据引用、人工复核边界和 `.docx` 解析限制等方面的安全合规设计。
> 主脚本：`scripts/gov_doc_review.py`。配套策略文件：`references/safety-policy.md`。

## 一、零联网、零外部 API、零第三方依赖

### 1. 不联网

脚本 `scripts/gov_doc_review.py` **不发起任何网络请求**。

- 不调用任何外部模型 API（OpenAI、Anthropic、本地模型服务等均不调用）。
- 不访问任何外部服务（不请求 URL、不连数据库、不发邮件、不上传文件）。
- 不做任何 DNS 解析、TCP 连接、HTTP 请求。
- 所有处理在本地内存中完成，处理完成后输出到 stdout 或用户显式指定的 `--output` 文件。

代码层面可验证：脚本仅 import 标准库（`argparse`、`csv`、`io`、`json`、`re`、`sys`、`zipfile`、`dataclasses`、`pathlib`、`typing`、`xml.etree.ElementTree`），不 import `urllib`、`requests`、`httpx`、`socket` 等任何网络相关模块。

### 2. 不调用外部 API

- 不调用任何大模型 API。
- 不调用任何公文知识库 API。
- 不调用任何 OCR、翻译、纠错等外部能力。
- 所有判断由脚本内置的规则启发式完成，结果可复现。

### 3. 零第三方依赖

脚本仅依赖 Python 标准库，**不需要 `pip install` 任何包**。

- 部署时无需配置虚拟环境、无需解决依赖冲突、无需担心供应链投毒。
- `.docx` 解析不依赖 `python-docx`，而是直接用标准库 `zipfile` + `xml.etree.ElementTree` 读取 OOXML。
- 适合在 AstronClaw / SkillHub 等受控环境、内网环境、离线环境稳定运行。

### 4. 不保存用户文档

- 脚本仅读取 stdin 或用户指定文件，处理完成后输出到 stdout 或指定输出文件。
- 不写入任何中间文件、不上传任何服务器、不缓存任何用户内容。
- 输出文件由用户显式指定（`--output`），否则只输出到 stdout。
- 处理完成后，用户文档不留存在脚本进程中（脚本退出即释放）。

## 二、本地 PII 脱敏

### 1. 脱敏规则

脚本识别到手机号、身份证号等个人敏感信息时，输出**本地脱敏预览**，脱敏规则如下：

| 字段 | 识别规则 | 脱敏规则 | 示例 |
| --- | --- | --- | --- |
| 手机号 | 正则 `1[3-9]\d{9}`（前后非数字边界） | 保留前 3 位 + 后 4 位，中间用 `****` 替换 | `13812345678` → `138****5678` |
| 身份证号 | 正则 `\d{17}[\dXx]` 或 `\d{15}`（前后非数字边界） | 保留前 6 位 + 后 4 位，中间用 `*` 替换 | `110101199001011234` → `110101********1234` |

### 2. 脱敏只在输出报告中展示

- 脱敏预览出现在审查报告的"六、脱敏预览"章节，是**展示用**的副本。
- **不修改用户原始文件**：脚本读取的是 stdin 或输入文件，输出的是 stdout 或 `--output` 文件，原始文件不会被改写。
- 脱敏预览的目的是让承办人"提交前确认"，而不是替代正式脱敏流程。

### 3. 同时给出风险提示

识别到 PII 时，脚本会在"承办人修改清单"中追加一条 high 级别问题：

- 问题名：疑似个人敏感信息
- 严重程度：high
- 修改建议：提交或上传前先脱敏；涉及个人信息的材料建议本地处理并人工复核。
- 依据：《个人信息保护法》个人信息处理的合法、必要、最小化原则

### 4. 风险等级强制提升

`score_document()` 中，只要存在"疑似个人敏感信息"或"疑似涉密或内部资料"问题，风险等级强制提升为"高"，避免"分数高但实际有敏感信息"的误判。

## 三、涉密材料检测（只提示，不处理）

### 1. 检测规则

脚本用正则 `涉密|绝密|机密|秘密|内部资料|不得外传|知悉范围|敏感材料` 检测涉密或内部资料表述。命中时：

- 在"承办人修改清单"中追加一条 high 级别问题：
  - 问题名：疑似涉密或内部资料
  - 严重程度：high
  - 修改建议：**不要上传涉密或未公开材料到外部平台**；在本地环境处理，并按单位保密要求标注密级、人工复核。
  - 依据：《保守国家秘密法》及涉密公文密级标注要求
- 风险等级强制提升为"高"。

### 2. 只提示，不处理

- 脚本**不会**对涉密材料做任何内容改写、摘要、翻译或上传。
- 脚本**不会**把涉密材料的内容输出到任何外部位置（只输出到本地 stdout 或用户指定的本地文件）。
- 脚本**不会**保存涉密材料到任何中间存储。
- 脚本只做一件事：**告诉用户"这看起来像涉密材料，请按保密要求处理"**。

### 3. 与人工保密审查的边界

- 脚本的涉密检测是**关键词启发式**，会有漏报（没命中关键词不代表一定不涉密）和误报（命中关键词不代表一定涉密）。
- 脚本**不替代**人工保密审查。最终是否涉密、定什么密级、如何处理，应由单位保密审查人员依据《保守国家秘密法》和单位保密制度判定。
- 脚本的提示价值在于：在用户**误把涉密材料丢给外部平台之前**，拦一下。

## 四、不编造政策依据

### 1. 依据只指向要素名称和原则

问题清单中引用的依据指向 GB/T 9704—2012 与《党政机关公文处理工作条例》的**要素名称和原则**，例如：

- "GB/T 9704—2012《党政机关公文格式》 主体·成文日期"
- "《党政机关公文处理工作条例》 报告与请示分立"
- "《党政机关公文处理工作条例》 请示一文一事"
- "《党政机关公文处理工作条例》 函的适用范围"
- "《个人信息保护法》个人信息处理的合法、必要、最小化原则"

### 2. 不编造具体条款号

- **不写**"第 X 条第 Y 款""根据国标第 Z 节"等具体条款序号。
- 原因：国标和条例会修订，具体条款号可能变化；模型和脚本都不应"幻觉"一个看似权威但并不存在的条款号。
- 用户如需引用具体条款，应以现行标准与条例正式文本为准，提交前人工核对。

### 3. 不编造法规名称、上级文件

- 不编造法规名称（如不编造"《XX 省公文处理办法》"）。
- 不编造上级文件（如不编造"根据 X 委〔2025〕X 号文件"）。
- 不编造不存在的政策。
- 涉及政策、法规、涉密材料、个人隐私和未公开政务数据时，应由用户提供依据并进行人工复核。

### 4. 依据映射可追溯

`references/basis-map.json` 提供问题类型到依据的结构化映射，保证输出依据统一、可追溯。每条问题的 `basis` 字段都可在该文件中找到对应条目，便于审计和复核。

## 五、人工复核边界

### 1. 结果仅作初审

- 本 Skill 输出结果仅作为**材料初审和起草辅助**，**不替代**：
  - 人工公文审核（格式、内容、政治性、政策性）。
  - 法律审核（合同、协议、规范性文件的合法性）。
  - 保密审查（涉密定级、知悉范围、脱密处理）。
- 最终应由人工复核后提交。

### 2. 校验层为规则启发式

- 脚本的检查规则是基于正则和行首特征的启发式，对"脏"输入会有少量误报/漏报。
- 例如：主送机关识别依赖"以冒号结尾且长度 ≤60"的启发式，遇到非常规格式可能漏识别。
- 例如：文种识别依赖标题关键词，遇到"关于……的若干意见"这类非标准标题可能误判为"通用材料"。
- 误报/漏报由智能体层（语义复核）和人工复核兜底。

### 3. 不承诺政策问答

- 本 Skill 聚焦公文格式校验、起草、修订建议、督办提取和版本对比。
- **不承诺**政策问答、政策依据核验、全量政务知识检索。
- 用户如需政策依据，应查阅现行有效的政策原文，或咨询业务主管部门。

## 六、.docx 解析限制

### 1. 提取范围

`.docx` 解析提取以下内容：

- **正文段落**：`word/document.xml` 中的所有 `w:p` 元素，拼接 `w:t` 文本。
- **表格文本**：`word/document.xml` 中的所有 `w:tbl` 元素，逐单元格（`w:tc`）提取文本，用 ` | ` 分隔单元格，换行分隔行。表格内容追加到正文之后，以 `[表格内容]` 标注。

### 2. 不解析的内容

以下内容**不纳入自动审查**：

- **页眉**（`word/header*.xml`）：版式信息，与正文合规性关系不大。
- **页脚**（`word/footer*.xml`）：同上。
- **版记**：公文末尾的版记信息（抄送、印发机关、印发日期等）不解析。
- **批注内容**（`word/comments.xml`）：检测到批注存在时会提示用户，但不解析具体批注内容。
- **修订内容**（`w:ins` / `w:del`）：检测到修订痕迹时会提示用户，但不解析具体修订内容（谁改的、改了什么）。
- **嵌入对象**（图片、图表、OLE 对象）：不解析。
- **样式信息**（字体、字号、行距、缩进）：不解析（公文格式国标对版式有要求，但脚本聚焦文本要素）。

### 3. 检测但不解析的信号

脚本会检测以下信号并在报告中提示：

| 信号 | 检测方式 | 提示内容 |
| --- | --- | --- |
| 批注 | `word/comments.xml` 是否存在于 docx 包 | "检测到批注：提交正式材料前请确认是否接受全部修订并删除批注" |
| 修订痕迹 | `w:ins` 或 `w:del` 元素是否存在 | "检测到修订痕迹：提交正式材料前请确认是否接受全部修订并删除批注" |
| 表格 | `w:tbl` 元素是否存在 | "含 N 个表格（已提取文本）" |

### 4. 损坏 docx 的处理

- 非 zip 文件（如把 `.txt` 改名成 `.docx`）→ `BadZipFile` → 返回 `# 输入提示`："无法解析 .docx 文件（可能不是有效的 Word 文档或文件已损坏）"。
- zip 文件但缺 `word/document.xml` → `KeyError` → 同上友好提示。
- `word/document.xml` 存在但 XML 解析失败 → `ParseError` → "docx 文档结构异常，无法提取正文"。
- **不抛 raw traceback**，所有异常都被 `InputError` 包装，由上层捕获并返回友好提示。

### 5. 非 UTF-8 文本的处理

- 读取 UTF-8 文本/Markdown/JSON 文件时，用 `encoding="utf-8", errors="replace"`。
- 遇到非法字节，用替换字符（U+FFFD）代替，**不抛异常**。
- stdin 读取时同样 `reconfigure(encoding="utf-8", errors="replace")`。
- 这样即使文件是 GBK、GB2312 等其他编码，脚本也能"尽量读出来"而不是崩溃。

## 七、合规依据

本 Skill 的安全合规设计参照以下法律法规与标准：

- **GB/T 9704—2012《党政机关公文格式》**：现行标准，国家标准全文公开系统可查。
- **《党政机关公文处理工作条例》**：强调公文处理要准确规范、精简高效、安全保密。
- **《中华人民共和国个人信息保护法》**：个人信息处理的合法、必要、最小化原则。
- **《中华人民共和国保守国家秘密法》**：涉密公文密级标注要求。
