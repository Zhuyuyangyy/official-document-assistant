# 3 分钟演示脚本

> 面向评委的 3 分钟演示，展示「公文合规审查与督办助手」（`official-document-assistant`，v0.8.0）的四个核心场景。
> 每个场景约 40 秒，总计约 3 分钟。演示前请确认已 `cd` 到项目根目录。

## 演示开场（10 秒）

> "各位评委好，我演示的是『公文合规审查与督办助手』。它解决的不是『帮你写公文』，而是办公室材料反复退回的真正痛点——格式要素不齐、文种混用、敏感信息没脱敏、会议待办没人跟。
>
> 它用两层架构：智能体层做语义理解和润色，确定性校验层做可复现、不幻觉的格式校验和脱敏。下面用四个场景展示。"

---

## Demo 1：审查一份问题通知（40 秒）

### 场景说明

> "第一场景：办公室新人写了一份通知，标题缺要素、日期格式不对、还夹了手机号。我们看脚本怎么审。"

### 运行命令

```bash
python scripts/gov_doc_review.py --mode review --format markdown --input examples/review/dirty-realistic.md
```

### 用户输入（examples/review/dirty-realistic.md）

```
XX市卫生健康委员会关于2025年度基层医疗工作情况的报告

市政府办公室：

现将我委2025年度基层医疗工作情况报告如下。一、基本情况，全年完成门诊量约120万人次。二、存在问题，部分乡镇卫生院设备老化。三、下一步打算，拟申请追加专项经费300万元，请予支持。

抄送：市财政局，市发展改革委。

XX市卫生健康委员会
2026-01-20
```

### Skill 输出（关键部分）

```markdown
# 公文材料审查报告

## 一、领导摘要

- 结论：存在中风险问题，建议按修改清单完善后提交。
- 风险等级：中
- 综合评分：84/100
- 文种识别：报告
- 主要问题：
  - [medium] 成文日期格式不规范：成文日期应用阿拉伯数字标注为"YYYY年M月D日"，不使用"-""/"等分隔符，月、日不编虚位。
  - [medium] 报告疑似夹带申请事项：报告应以陈述情况为主，需审批或支持事项建议另行请示。

## 三、承办人修改清单

| 序号 | 严重程度 | 问题 | 原文证据 | 修改建议 | 依据 |
| --- | --- | --- | --- | --- | --- |
| 1 | medium | 成文日期格式不规范 | 2026-01-20 | 成文日期应用阿拉伯数字标注为"YYYY年M月D日"... | GB/T 9704—2012《党政机关公文格式》 主体·成文日期 |
| 2 | medium | 报告疑似夹带申请事项 | ...拟申请追加专项经费300万元，请予支持。 | 报告应以陈述情况为主... | 《党政机关公文处理工作条例》 报告与请示分立 |
```

### 评委关注点（Highlight）

> "注意三点：
> 1. **三层报告**：领导摘要 10 秒看结论，承办人清单逐条改，建议修订稿可直接复制——对应办公室三个角色。
> 2. **依据可追溯**：每条问题都指向 GB/T 9704—2012 或条例的具体要素，不是泛泛说'格式不对'。
> 3. **报告夹带请示**：脚本识别出'拟申请追加专项经费300万元，请予支持'是请示性表述，提醒'报告不得夹带请示事项'——这是公文写作的高频错误。"

## Demo 2：起草一份请示（40 秒）

### 场景说明

> "第二场景：用户想起草一份请示，但只给了一句话。脚本不仅生成草稿，还自动跑一遍合规自检。"

### 运行命令

```bash
python scripts/gov_doc_review.py --mode draft --format markdown --input examples/draft/request.txt
```

### 用户输入（examples/draft/request.txt）

```
请帮我写一份请示，主题是申请采购办公电脑，报给信息中心
```

### Skill 输出（关键部分）

```markdown
# 起草结果

## 一、可编辑草稿

```text
关于申请采购办公电脑的请示

信息中心：

为保障采购办公电脑相关工作顺利开展，现就有关事项请示如下：

一、请示事项
拟申请采购办公电脑，用于保障日常办公和业务办理需要。

二、主要理由
当前相关工作对采购办公电脑提出了实际需求，现有条件难以充分满足后续工作开展。为提高工作效率、保障任务落实，建议予以支持。

三、拟办建议
1. 明确责任分工。
2. 按时报送进展。
3. 确保工作落实。

妥否，请批示。

发文单位
XXXX年XX月XX日
```

## 二、起草信息缺口

- 未提供主送机关，已暂用默认称谓。
- 未提供落款单位，已暂用"发文单位"。
- 未提供截止时间，已标注为"明确时间节点"。
- 未提供具体要求，已使用默认工作要求占位。

## 三、自动合规自检

| 序号 | 严重程度 | 问题 | 修改建议 |
| --- | --- | --- | --- |
| 1 | medium | 缺少落款单位 | 在成文日期上一行补充发文机关署名。 |
| 2 | high | 缺少成文日期 | 补充成文日期，用阿拉伯数字标注为"YYYY年M月D日"，月、日不编虚位。 |
| 3 | medium | 正文层级可能混用 | 正文层次序数依次用"一、""（一）""1.""（1）"，避免层级跳跃。 |
| 4 | medium | 请示可能不符合一文一事 | 请示应坚持一文一事，多个事项建议拆分或明确主次。 |

> 自检评分：62/100；风险等级：高。
```

### 评委关注点（Highlight）

> "注意三点：
> 1. **起草即自检**：草稿生成后自动跑一遍 review，输出'草稿 + 信息缺口 + 自检报告'，不用用户再手动审查一遍。
> 2. **信息缺口透明**：脚本明确告诉用户'你没给落款单位、没给截止时间'，并用占位符标注，避免模型编造。
> 3. **自检诚实**：脚本不会因为'这是自己生成的草稿'就手下留情——缺落款、缺日期、层级混用、一文多事都如实指出，风险等级判为'高'。"

## Demo 3：会议纪要转督办台账（40 秒）

### 场景说明

> "第三场景：开完会，会议纪要里散落着待办事项。脚本提取责任方、截止时间，输出可贴入 Excel 的督办台账。"

### 运行命令

```bash
# Markdown 表格
python scripts/gov_doc_review.py --mode brief --format markdown --input examples/brief/meeting.md

# CSV（带 UTF-8 BOM，Excel 直接打开）
python scripts/gov_doc_review.py --mode brief --format csv --input examples/brief/meeting.md
```

### 用户输入（examples/brief/meeting.md）

```
会议纪要

会议要求，办公室于6月18日前完成通知发布。
请财务处负责经费测算，6月25日前提交预算表。
各部门要及时落实材料报送要求。
```

### Skill 输出（Markdown 表格）

```markdown
# 会议督办台账

| 序号 | 责任单位 | 待办事项 | 截止时间 | 原文依据 | 建议状态 |
| --- | --- | --- | --- | --- | --- |
| 1 | 办公室 | 完成通知发布 | 6月18日前 | 会议要求，办公室于6月18日前完成通知发布 | 未开始 |
| 2 | 财务处 | 经费测算，提交预算表 | 6月25日前 | 请财务处负责经费测算，6月25日前提交预算表 | 未开始 |
```

### Skill 输出（CSV，带 UTF-8 BOM）

```
序号,责任单位,待办事项,截止时间,原文依据,建议状态
1,办公室,完成通知发布,6月18日前,会议要求，办公室于6月18日前完成通知发布,未开始
2,财务处,经费测算，提交预算表,6月25日前,请财务处负责经费测算，6月25日前提交预算表,未开始
```

### 评委关注点（Highlight）

> "注意三点：
> 1. **结构化提取**：从自然语言会议纪要中提取出责任方（办公室/财务处）、待办事项、截止时间，并附原文依据可追溯。
> 2. **CSV 带 BOM**：输出的 CSV 带 UTF-8 BOM，Excel 直接双击打开中文不乱码，可直接贴入任务系统。
> 3. **第三句被跳过**：'各部门要及时落实材料报送要求'没有明确责任方和截止时间，脚本不会硬凑，避免编造督办事项。"

## Demo 4：版本对比（40 秒）

### 场景说明

> "第四场景：通知改了一版，领导问'这版和上版比改了什么？风险变了吗？'脚本对比两版，输出核心变化和风险变化。"

### 运行命令

```bash
python scripts/gov_doc_review.py --mode compare --old examples/compare/old.md --new examples/compare/new.md --format markdown
```

### 用户输入

**旧版本（examples/compare/old.md）**：

```
关于开展培训的通知

各部门：
请尽快完成培训报名，并将结果报办公室。

办公室
2026-07-01
```

**新版本（examples/compare/new.md）**：

```
关于开展办公技能培训的通知

各部门：
为提升员工办公技能，现决定开展办公技能培训。请各部门于2026年7月10日前完成报名，并将名单报办公室。联系人：张老师，联系电话：13812345678。

办公室
2026年7月1日
```

### Skill 输出（关键部分）

```markdown
# 文档版本变更说明

## 一、核心变化

- **标题**：由"关于开展培训的通知"改为"关于开展办公技能培训的通知"（标题已修改）。
- **成文日期**：由"2026-07-01"改为"2026年7月1日"（成文日期已调整）。
- **正文字数**：由"34"改为"91"（正文篇幅明显变化）。

## 二、风险变化

| 项目 | 旧版本 | 新版本 | 变化 |
| --- | --- | --- | --- |
| 风险等级 | 低 | 高 | 风险上升 |
| 综合评分 | 92/100 | 86/100 | 下降 |
| 新增风险点 | — | 疑似个人敏感信息 | 需关注 |
| 已解决风险点 | 成文日期格式不规范 | — | 风险降低 |

## 三、提交建议

新版本风险上升，建议先处理新增风险点（如脱敏、补主送机关、修正日期格式）后再提交。
```

### 评委关注点（Highlight）

> "注意三点：
> 1. **风险变化表**：旧版风险'低'（92 分），新版风险'高'（86 分）——虽然分数只降了 6 分，但风险等级从'低'跳到'高'，因为新版引入了手机号（PII），触发了风险等级强制提升规则。同时旧版的'成文日期格式不规范'在新版中已解决。
> 2. **提交建议**：脚本给出明确建议——'新版本风险上升，建议先处理新增风险点（脱敏）后再提交'，不是泛泛说'请人工复核'。
> 3. **日期格式修正**：旧版日期是'2026-07-01'（不规范），新版改成'2026年7月1日'（规范），脚本识别出这一变化并记为'已解决风险点'。"

---

## 演示收尾（10 秒）

> "四个场景演示完毕。总结本 Skill 的三个卖点：
> 1. **可解释**：每条问题给出 GB/T 9704—2012 / 条例依据，不只给泛泛修改建议。
> 2. **可落地**：审查、修订、起草、督办、版本对比五步覆盖办公室真实流程。
> 3. **可控安全**：确定性脚本本地运行，不联网，敏感信息先脱敏，涉密材料只提示不处理。
>
> 谢谢各位评委。"
