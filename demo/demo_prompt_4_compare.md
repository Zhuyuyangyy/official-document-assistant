# 演示场景 4：版本变更说明

> 用户给出两版通知，Skill 对比标题/主送机关/日期/风险变化，输出核心变化、风险变化表和提交建议。

## 用户输入

用户在智能体对话框中说：「我改了一版通知，帮我对比一下这版和上版有什么变化，风险有没有变。」

用户提供了两个文件：

**旧版本（examples/compare/old.md）**：

```
关于开展培训的通知

各部门：
请尽快完成培训报名，并将结果报办公室。

办公室
2026-07-01
```

**新版本（examples/compare/new.md）**：

```
关于开展办公技能培训的通知

各部门：
为提升员工办公技能，现决定开展办公技能培训。请各部门于2026年7月10日前完成报名，并将名单报办公室。联系人：张老师，联系电话：13812345678。

办公室
2026年7月1日
```

## 智能体调用

智能体识别意图为版本对比，调用确定性校验层脚本：

```bash
python scripts/gov_doc_review.py --mode compare --old examples/compare/old.md --new examples/compare/new.md --format markdown
```

## Skill 输出

```markdown
# 文档版本变更说明

## 一、核心变化

- **标题**：由"关于开展培训的通知"改为"关于开展办公技能培训的通知"（标题已修改）。
- **成文日期**：由"2026-07-01"改为"2026年7月1日"（成文日期已调整）。
- **正文字数**：由"34"改为"91"（正文篇幅明显变化）。

## 二、风险变化

| 项目 | 旧版本 | 新版本 | 变化 |
| --- | --- | --- | --- |
| 风险等级 | 低 | 高 | 风险上升 |
| 综合评分 | 92/100 | 86/100 | 下降 |
| 新增风险点 | — | 疑似个人敏感信息 | 需关注 |
| 已解决风险点 | 成文日期格式不规范 | — | 风险降低 |

## 三、提交建议

新版本风险上升，建议先处理新增风险点（如脱敏、补主送机关、修正日期格式）后再提交。
```

## 评委关注点

1. **风险变化表一目了然**：旧版风险"低"（92 分），新版风险"高"（86 分）——虽然分数只降了 6 分，但风险等级从"低"跳到"高"，因为新版引入了手机号（PII），触发了风险等级强制提升规则。
2. **新增风险 vs 已解决风险**：新版新增了"疑似个人敏感信息"（手机号 13812345678），同时解决了旧版的"成文日期格式不规范"（旧版用 `2026-07-01`，新版改成 `2026年7月1日`）。脚本把两侧的风险变化对比清楚，不是只说"改了什么"。
3. **提交建议可执行**：脚本给出明确建议——"新版本风险上升，建议先处理新增风险点（如脱敏、补主送机关、修正日期格式）后再提交"，不是泛泛说"请人工复核"。
4. **核心变化覆盖关键要素**：标题（更明确了）、成文日期（格式修正了）、正文字数（篇幅明显变化）——这些都是办公室流转中需要关注的变更点。
5. **复用审查能力**：compare 模式对旧版和新版各跑一遍 review，对比两侧的风险等级和问题集合。这是"审查能力"的复用，体现了五模式的可组合性。
